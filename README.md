# Predictive Maintenance & Manufacturing Quality Analysis

**Live app:** [https://manufacturing-quality-analysis-defect-prediction-mkbvjywxtqkhq.streamlit.app](https://manufacturing-quality-analysis-defect-prediction-mkbvjywxtqkhq.streamlit.app)

A reproducible, modular Python machine learning workflow for industrial predictive maintenance and quality inspection, built using the [UCI AI4I 2020 Predictive Maintenance Dataset](https://archive.ics.uci.edu/ml/machine-learning-databases/00601/ai4i2020.csv) (Matzka 2020).

---

## 📌 Project Overview & Tracks

This repository investigates two distinct manufacturing prediction paradigms:

1. **Track 1: Predictive Maintenance on UCI Sensor Columns (Primary)**<br>
   Trains ML pipelines on the five original UCI AI4I 2020 sensor columns (`air_temperature_k`, `process_temperature_k`, `rotational_speed_rpm`, `torque_nm`, `tool_wear_min`), plus three features derived from them, to predict the UCI `Machine failure` label (`source_machine_failure`).
2. **Track 2: Dimensional Tolerance Analysis (Leakage Demonstration)**<br>
   Uses workpiece measurements (`length_mm`, `weight_g`) that **this project generated** from the sensor data. It is kept to demonstrate **synthetic-label leakage**.

> [!IMPORTANT]
> AI4I 2020 is itself a **synthetic** benchmark (UCI: *"a synthetic dataset that reflects real predictive maintenance data"*). Its failure label is produced by published rules on these same sensor columns. Nothing in this repository is real factory data.

## 🖥️ Streamlit App

A five-page dashboard (`app.py`) wraps the existing code. It never trains a model: it loads the saved pipeline once and reads the files in `reports/`.

| Page | What it does |
| :--- | :--- |
| **Overview** | Introduces both workflows and shows the saved model's results on unseen rows, read from `reports/metrics.json` |
| **Predictive Maintenance** | Takes five validated sensor readings and returns the saved model's failure prediction and probability, through the same `predict_machine_failure` the CLI uses. Example presets are sample readings only. |
| **Part Quality Inspection** | Applies the Track 2 label rule (machine failure, or \|tolerance deviation\| > 0.12 mm, or \|weight − 250 g\| > 7 g) using the generator's own constants. It's a deterministic rule, not a model. |
| **Analytics & Evaluation** | Train-split, test-split and unseen-row metrics, confusion matrices, the classification report, feature importance and EDA figures |
| **About the Project** | Data provenance, pipeline, evaluation method and limitations |

Every page carries a synthetic-data notice. Probabilities are model estimates, not calibrated real-world risks.

## 🔬 Source Data vs. Project-Generated Measurements

```
┌────────────────────────────────────────────────────────────────────────┐
│          SOURCE COLUMNS — copied unchanged from UCI AI4I 2020           │
│          (synthetic benchmark; verified 0 difference vs. raw CSV)       │
│                                                                        │
│  - air_temperature_k, process_temperature_k                            │
│  - rotational_speed_rpm, torque_nm, tool_wear_min                      │
│  - source_machine_failure   : UCI rule-based failure label (0/1)       │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ scripts/adapt_ai4i_dataset.py
                                    ▼ (formulas + random noise)
┌────────────────────────────────────────────────────────────────────────┐
│               GENERATED BY THIS PROJECT — not measurements             │
│                                                                        │
│  - length_mm, width_mm, height_mm, weight_g, tolerance_deviation_mm    │
│  - defective = failure OR |tol_dev| > 0.12 OR |weight − 250| > 7       │
└────────────────────────────────────────────────────────────────────────┘
```

> [!WARNING]
> **Synthetic-label leakage.** `defective` is computed from the same generated columns that Track 2 uses as features, so trees recover the thresholds and score 97.5–98.5% accuracy (rerun verified). Track 1 removes this *project-made* circularity. It does **not** give real-world evidence, because the UCI label is also rule-generated from the sensor columns.

The exact generator formulas, UCI failure rules, sampling caveats and data dictionary are in [docs/DATASET_CARD.md](docs/DATASET_CARD.md).

## 📊 Track 1 Verified Performance & Metrics

Measured on 2 Nov 2026 with `python3 src/train.py`. Models use the five sensors plus three derived features: temperature difference, power (`torque × rpm × 2π/60`) and strain (`tool_wear × torque`). A run is flagged as a failure at a probability of 0.4 or more, on the assumption that a missed failure costs more than an inspection.

### Cross-Validated Performance (use this to compare models)

Stratified 5-fold cross-validation repeated 5 times on all 1,000 rows (mean ± standard deviation across folds). The failure rate here is oversampled to 15%; the UCI source rate is 3.39%:

| Model | Failure Precision | Failure Recall | F1-Score |
| :--- | :---: | :---: | :---: |
| Decision Tree | 0.842 ± 0.072 | 0.809 ± 0.065 | 0.822 ± 0.048 |
| Logistic Regression | 0.737 ± 0.088 | 0.591 ± 0.064 | 0.653 ± 0.059 |
| **Random Forest (300 trees, saved model)** | **0.858 ± 0.062** | **0.843 ± 0.055** | **0.848 ± 0.043** |
| Previous model: Random Forest (50 trees), sensors only, threshold 0.5 | 0.794 ± 0.065 | 0.747 ± 0.077 | 0.765 ± 0.043 |

### Unseen UCI Rows (hardest check)

The 9,000 raw UCI rows outside the training sample, with 189 failures (2.10%). These rows are for reporting only, not for choosing models or thresholds. Because failures are rare here, precision is much lower than in the oversampled tables:

| Model | Failure Precision | Failure Recall | F1-Score | False Alarms | Missed Failures (of 189) |
| :--- | :---: | :---: | :---: | :---: | :---: |
| Previous model (threshold 0.5) | 0.344 | 0.810 | 0.483 | 292 | 36 |
| **Saved model (threshold 0.4)** | **0.447** | **0.894** | **0.596** | **209** | **20** |
| Same new model at threshold 0.5, for comparison | 0.601 | 0.878 | 0.714 | 110 | 23 |

Threshold 0.4 catches 3 more failures than 0.5 on these rows but raises 99 more false alarms. Change `FAILURE_THRESHOLD` in `src/pipeline.py` if false alarms are the larger cost.

### Single Test Split

Held-out stratified test set ($n = 200$: 170 normal runs, 30 failures). One failure is worth 3.3 recall points, so don't compare models on this table:

| Model Architecture | Train Acc | Test Acc | Failure Precision | Failure Recall | F1-Score | Confusion Matrix (Normal / Failure) |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| **Decision Tree** | 1.0000 | 0.9450 | 0.8065 | 0.8333 | 0.8197 | `[[164, 6], [5, 25]]` |
| **Logistic Regression** | 0.9075 | 0.9300 | 0.8636 | 0.6333 | 0.7308 | `[[167, 3], [11, 19]]` |
| **Random Forest (300 trees, saved model)** | 1.0000 | 0.9750 | 0.9630 | 0.8667 | 0.9123 | `[[169, 1], [4, 26]]` |

### 🧠 Key Engineering Takeaways

1. **Why the derived features help**: UCI's failure rules depend on these sensor combinations, which are hard for trees to approximate from raw sensors. On the unseen rows, the saved model catches every heat, power and overstrain failure.
2. **What still gets missed**: on the unseen rows it catches 6 of 22 tool wear failures and 0 of 19 random failures. Those modes are partly or fully random by design, so recall can't reach 100% from sensors alone.
3. **What these numbers do and don't mean**: the derived features are essentially UCI's own formulas, so the gain shows the model recovering the rules that generated a synthetic label. It is not evidence of real-factory performance.
4. **Leakage-Free Preprocessing**: `SimpleImputer` and `StandardScaler` are encapsulated inside Scikit-learn `Pipeline` objects and fitted **only** on training data. The derived features use each row's own values, so they learn nothing from other rows.

* **Benchmark Grounding**: Sourced from the peer-reviewed **AI4I 2020 Predictive Maintenance Dataset** (Matzka 2020, UCI Machine Learning Repository).
* **Sample Size & Statistical Power**: With $n = 1,000$ (800 train, 200 test), each test classification error represents a $0.5\%$ accuracy change. With only 30 test failures, each missed failure moves recall by 3.3 points, so small gaps between models are not reliable.

## 🚀 Quickstart & Usage

### 1. Installation (macOS)
Clone the repository, then install the pinned dependencies in a virtual environment. Use Python 3.15, the version these pins and the saved model were verified on:
```bash
git clone https://github.com/Ronitshah042/Manufacturing-Quality-Analysis-Defect-Prediction.git
cd Manufacturing-Quality-Analysis-Defect-Prediction
python3.15 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```
Run the commands below from the repository root with the environment active.

**In VS Code:** open the repository folder, then choose **Python: Select Interpreter** from the Command Palette (⇧⌘P) and pick `./.venv/bin/python`. New terminals then activate the environment automatically.

### 2. Run the Streamlit App
```bash
streamlit run app.py
```
It opens at http://localhost:8501. Stop it with Ctrl+C.

### 3. Run Unit Tests
Execute the automated test suite. It covers the pipeline, predictions, the saved model, dataset regeneration, the report files, the app's validation and rule logic, and a headless run of every app page:
```bash
python3 -m unittest discover -s tests -v
```

### 4. Train & Evaluate Models
Train the baseline pipeline, compare against Logistic Regression and Random Forest, and save the fitted model:
```bash
python3 src/train.py
```

### 5. Run Predictive Maintenance Inspections
Predict machine failure risk using the serialized pipeline:

**Run the built-in industrial demonstration suite**:
```bash
python3 src/predict.py
```

**Predict for specific machine sensor readings via CLI**:
```bash
# Normal milling operation
python3 src/predict.py --air_temp 298.2 --process_temp 308.7 --rpm 1500 --torque 40.0 --tool_wear 40

# Overstrain cutting load risk
python3 src/predict.py --air_temp 301.2 --process_temp 311.5 --rpm 1280 --torque 69.8 --tool_wear 195

# Critical tool wear breakdown risk
python3 src/predict.py --air_temp 300.4 --process_temp 310.8 --rpm 1410 --torque 52.0 --tool_wear 235
```

## 📈 EDA and Evaluation Report

To write the Track 1 figures and tables to `reports/`:
```bash
python3 src/report.py
```
* `eda_sensor_distributions.png`: each model input, normal runs vs. failures.
* `eda_failure_rules.png`: the UCI power and overstrain rules drawn over the data.
* `confusion_matrix.png` and `classification_report.txt`: results on the test split and the unseen UCI rows.
* `feature_importance.png` and `feature_importance.csv`: permutation and impurity importance.

[docs/EVALUATION.md](docs/EVALUATION.md) shows each figure and explains how to read it.

```bash
python3 manufacturing_visualizations.py
```
* `manufacturing_dimension_boxplots.png`: 4-panel distribution comparison for weight, length, width, and height.
* `manufacturing_scatter_plot.png`: inspection map with the 0.12 mm tolerance and 243–257 g weight limits.

## ☁️ Deploying to Streamlit Community Cloud

The app is deployed at [https://manufacturing-quality-analysis-defect-prediction-mkbvjywxtqkhq.streamlit.app](https://manufacturing-quality-analysis-defect-prediction-mkbvjywxtqkhq.streamlit.app) from the `main` branch, so every push to `main` redeploys it automatically. To deploy your own copy:

1. Push the latest code to GitHub.
2. Sign in at https://share.streamlit.io with your GitHub account and choose **Create app**.
3. Select the repository, branch `main`, and main file `app.py`. The repository must be public, or Streamlit must be given access to private repositories.
4. Under **Advanced settings**, choose Python 3.15. The saved model was built with the pinned scikit-learn on Python 3.15. If 3.15 isn't offered, pick the closest version, then retrain and rerun the tests on that version before deploying.
5. Choose **Deploy**. The app needs no secrets.

`.streamlit/config.toml` sets the theme. Cloud uses it automatically.

Free apps sleep after a period without visitors. `.github/workflows/keep-awake.yml` opens the live app in a headless browser every 6 hours using `scripts/keep_awake.py`, wakes it if needed, and fails, which sends you an email, if the app doesn't load.
