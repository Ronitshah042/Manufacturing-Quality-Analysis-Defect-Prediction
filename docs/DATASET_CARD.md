## 1. Column provenance

### Group A — Copied unchanged from UCI AI4I 2020 (used by Track 1)

Checked by joining on `UDI` against the raw UCI CSV: all 1,000 rows matched, and every column below had a max absolute difference of **0**.

| Column | UCI column | Range in this file | Track 1 role |
| :--- | :--- | :--- | :--- |
| `air_temperature_k` | Air temperature [K] | 295.6 – 304.4 | Feature |
| `process_temperature_k` | Process temperature [K] | 306.1 – 313.7 | Feature |
| `rotational_speed_rpm` | Rotational speed [rpm] | 1226 – 2874 | Feature |
| `torque_nm` | Torque [Nm] | 4.2 – 75.4 | Feature |
| `tool_wear_min` | Tool wear [min] | 0 – 246 | Feature |
| `source_machine_failure` | Machine failure | 0 / 1 | **Target** |
| `failure_type` | Derived from TWF/HDF/PWF/OSF/RNF flags | see §3 | Not used (reference only) |
| `product_id` | `PART-` + UCI `UDI` (zero-padded) | PART-0001 – PART-9994 (not contiguous) | Excluded (identifier) |

The UCI `Type` (L/M/H product quality) column is **not** included, even though UCI uses it in the overstrain rule (see §2).

### Group B — Generated by this project (used only by Track 2 / EDA scripts)

These columns are made with formulas and random noise in `adapt_ai4i_dataset.py`. They are **not** real measurements. No CMM, scale or micrometer data exists behind them.

| Column | How it is generated (exact code logic) | Range in this file |
| :--- | :--- | :--- |
| `tolerance_deviation_mm` | `(tool_wear − 100)/250 × 0.18 + (ΔT − 10)/4 × 0.05 + N(0, 0.02)`; for failure rows add `±U(0.12, 0.25)` | −0.289 – 0.375 |
| `length_mm` | `100.00 + tolerance_deviation_mm` (exactly; verified) | 99.711 – 100.375 |
| `width_mm` | `50.00 + 0.5 × tol_dev + N(0, 0.015)` | 49.844 – 50.191 |
| `height_mm` | `25.00 + 0.25 × tol_dev + N(0, 0.01)` | 24.918 – 25.102 |
| `weight_g` | `250 + (torque − 40)/20 × 4.5 − (rpm − 1500)/300 × 2.0 + N(0, 0.8)`; for failure rows add `±U(5, 12)`; then 8 values randomly set to NaN | 220.82 – 270.67 (8 NaN) |
| `defective` | `source_machine_failure == 1  OR  |tol_dev| > 0.12  OR  |weight_g − 250| > 7.0` | 181 True / 819 False |

ΔT = `process_temperature_k − air_temperature_k`. The 8 NaN weights are artificial missing values, added to practice imputation.

## 2. Two separate label-leakage problems

### 2a. Project-generated leakage (Track 2: `defective`)

`defective` is a deterministic function of columns in the same file. Recomputing the rule above matches all 1,000 rows (0 mismatches). In detail:

- All **150** machine-failure rows are labelled `defective`, and the generator also adds a large ±0.12–0.25 mm and ±5–12 g shift to exactly those rows. Failures are pushed past the same thresholds that define the label.
- `length_mm` is `100 + tolerance_deviation_mm`, so a model given `length_mm` effectively sees the tolerance variable used in the rule.

Rerun on 31 Oct 2026 (features `weight_g`, `length_mm`; target `defective`; same 80/20 stratified split, `random_state=42`):

| Model | Test accuracy | Defect recall | F1 | Confusion matrix |
| :--- | :---: | :---: | :---: | :---: |
| Decision Tree | 0.9750 | 0.9167 | 0.9296 | `[[162, 2], [3, 33]]` |
| Random Forest (50) | 0.9850 | 0.9167 | 0.9565 | `[[164, 0], [3, 33]]` |

These scores show how well a tree can recover the generator's thresholds. They say nothing about real inspection quality. All 3 missed defects pass both dimensional thresholds (`|tol_dev| ≤ 0.12` and `|weight_g − 250| ≤ 7`). They are labelled `defective` only through the `source_machine_failure` term, which the model cannot see. 18 rows in the file are defective for that reason alone (verified).

### 2b. Upstream rule-based labels (Track 1: `source_machine_failure`)

According to UCI's documentation, `Machine failure = 1` when **any** of these fires:

| Mode | UCI rule | Inputs available to Track 1? |
| :--- | :--- | :--- |
| HDF | air–process ΔT < 8.6 K **and** rpm < 1380 | Yes (all three) |
| PWF | power = torque × rpm·2π/60 outside 3500–9000 W | Yes |
| OSF | tool_wear × torque > 11,000 / 12,000 / 13,000 min·Nm for Type L / M / H | Partly. **`Type` is dropped** |
| TWF | tool replaced or fails at a random wear time between 200–240 min | Partly. Random component |
| RNF | 0.1% random failure regardless of inputs | No. Pure noise |

So Track 1 is also learning a hand-written rule system. Most of the failure signal (HDF, PWF, most of OSF) is a deterministic function of the five features. That is why tree models do well. The remaining errors come mostly from the dropped `Type` column, the random parts of TWF/RNF, and the limited training data (120 failures). They do not come from real-world sensor noise.

**What Track 1 does fix:** the project no longer grades models against a label that the project itself created from the model's own inputs.
**What it does not show:** performance on real machines.

## 3. Sampling and label caveats

- **Oversampled failures.** The generator takes all 150 sampled failures plus 850 random normal runs. That gives a **15.0%** failure rate, versus **3.39%** (339/10,000) in the UCI source. Precision, F1 and accuracy on this file are therefore **more optimistic** than they would be at the true prevalence. Recall is less affected.
- **`failure_type` is a simplification.** It keeps only the first matching flag in the order TWF → HDF → PWF → OSF → RNF.
  - 8 of the 150 failure rows have more than one mode flagged.
  - 5 rows have `source_machine_failure = 1` but **no** mode flag in UCI, and are labelled `"Normal Operation"`.
  - Use `source_machine_failure` as the target, never `failure_type`.
- **Single split.** All reported metrics come from one 200-row test set with 30 failures. One failure is worth 3.3 recall points, so differences of a few points between models are not reliable.

## 4. Track 1 results (rerun 31 Oct 2026)

Command: `/usr/bin/python3 src/train.py`. Features: the five Group A sensor columns. Target: `source_machine_failure`. Stratified 80/20 split, `random_state=42`. Test set n = 200 (170 normal, 30 failure).

| Model | Train acc | Test acc | Failure precision | Failure recall | F1 | Confusion matrix `[[TN, FP], [FN, TP]]` |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| Decision Tree | 1.0000 | 0.9250 | 0.8000 | 0.6667 | 0.7273 | `[[165, 5], [10, 20]]` |
| Logistic Regression | 0.9012 | 0.9100 | 0.9286 | 0.4333 | 0.5909 | `[[169, 1], [17, 13]]` |
| Random Forest (50) | 1.0000 | 0.9700 | 0.9615 | 0.8333 | 0.8929 | `[[169, 1], [5, 25]]` |

The saved model `models/defect_pipeline.joblib` is the Random Forest row. Its predictions and probabilities on all 1,000 rows match a fresh retrain exactly.

How to read these numbers:
- Logistic Regression's low recall fits the label structure. HDF, PWF and OSF are interaction / product rules (e.g. torque × rpm, wear × torque), which a linear model on raw features cannot represent.
- The Random Forest misses 5 of 30 failures. That is consistent with the unmodelled `Type`, TWF and RNF parts described in §2b.
- Accuracy is not a useful headline: predicting "normal" for every row already scores 0.85 here.
